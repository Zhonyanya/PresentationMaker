# GigaChat ML: настройка и рабочий профиль

`backend/presentation_ml` реализует внешний интерфейс из `ML_CONTRACT.md`.
Генерация и правка делают не более одного запроса к модели на операцию.
Явная неподдерживаемая структурная команда может быть отклонена без запроса.
Автоматических платных повторов, LLM-судьи и подмены ошибочного ответа fixture нет.

## Текущий выбор

| Уровень | Значение | Что означает |
|---|---|---|
| Модель | `GigaChat-3-Ultra` | Текущая модель пользователя; другие модели/провайдеры отложены |
| HTTP API | `https://api.giga.chat/v1` | Версия API провайдера |
| Промпт | `PM_ML_PROMPT_VERSION=v4` | Рабочий профиль содержания, теперь по умолчанию |
| Внутренний формат правки | `revision-wire-v3` | Формат ответа модели; внешний ML-контракт не менялся |
| Правила структуры генерации | `generation-wire-v1` | Титульный и заключительный входят в общее число слайдов |

Эти номера версий независимы. Основание выбора и ограничения —
[синтетическая оценка](ML_EVALUATION_2026_11_01.md). Выбор v4 не означает
доказанную точность на любых докладах или готовность production.

## Ключ и сертификат

В игнорируемом `backend/.env` задаются:

```dotenv
GIGACHAT_CREDENTIALS=<Authorization key проекта>
GIGACHAT_SCOPE=GIGACHAT_API_PERS
GIGACHAT_MODEL=GigaChat-3-Ultra
PM_ML_PROMPT_VERSION=v4
```

Нужен Authorization key, не Client ID и не временный access token. Официальный
SDK получает и обновляет токен самостоятельно; менять ключ каждые 30 минут
не требуется. Ключ передаётся только worker, не frontend и не API readiness.
Не выводите `.env`, токены, доклады и команды в журналы.

`compose.gigachat.yaml` подключает env_file к worker, включает модуль на api/worker
и монтирует публичный `backend/certs/gigachat-root.crt` только для чтения.
Проверка TLS включена. Сертификат получен по ссылке официальной документации;
его нужно обновить при изменении цепочки доверия. Никогда не помещайте секреты
в сертификат и не отключайте проверку TLS для обхода сетевого сбоя.

## Запуск

Обычный `compose.yaml` намеренно использует fixture. Реальная модель включается
явным override:

```bash
docker compose -f compose.yaml -f compose.gigachat.yaml build api
docker compose -f compose.yaml -f compose.gigachat.yaml up --no-build -d --wait
docker compose -f compose.yaml -f compose.gigachat.yaml exec web nginx -s reload
```

Сайт: `http://localhost:8080`. Готовность: `/api/v1/health/ready` →
`{"status":"ok","ml_adapter":"module"}`. Readiness проверяет импорт и интерфейс,
а не авторизацию или качество модели. Импорт не загружает SDK и не делает inference.

После пересоздания api в этом стенде наблюдался 502 через nginx при здоровом API;
`nginx -s reload` восстановил доступ. Проверяйте readiness через публичный порт
после обновления контейнеров. Не принимайте прямую проверку контейнера за проверку
всего пути через web.

Общий backend-образ достаточно собрать один раз через `build api`.
Для обновления только ML можно пересоздать api/worker с `--no-deps --no-build`,
затем перезагрузить nginx. Одновременная сборка нескольких сервисов с тем же
тегом образа ранее вызывала конфликт экспорта образа.

Если меняется только ключ или профиль окружения, пересоздайте worker:

```bash
docker compose -f compose.yaml -f compose.gigachat.yaml up --no-build --no-deps -d --force-recreate worker
```

В личном проекте оставляйте один одновременный запрос. Не запускайте CLI-проверку
параллельно с заданиями сайта на том же аккаунте. Несколько независимых стендов
потребуют общего ограничителя. Настоящий production остаётся отдельной задачей.

## Генерация и нормализация

PDF, DOCX и обычный текст используют общий формат блоков источника.
Импорт PDF/DOCX создаёт обычное сохранённое задание генерации. В генерацию
передаётся полный читаемый текст источника в пределах входного лимита, включая
таблицы и подписи. Граф добавляет ограниченный набор фактов с адресами блоков и
строк. Его правила распознают отдельные конструкции, поэтому покрытие графа
не ограничивает содержимое исходного текста. Правка видит сохранённый источник.

Режим сравнений использует ту же очередь и срок задания. Перед отбором
кандидатов остаются только отношения `metric_comparison`. Модель получает до
трёх кандидатов на одно свободное место после обложки и финала. Каждый выбранный
факт сверяется с группой, показателем, периодами и значениями исходной строки.
При отсутствии подходящих строк запрос к модели не отправляется. Работа с
изображениями в сохранённых слайдах и приёмка на реальных докладах остаются
отдельными этапами.

### План слайдов v4

Обычная генерация v4 с `SourceDocument` получает за один запрос массив `plan`
и слайды в том же порядке. Каждый пункт плана содержит цель, тезис, замысел
визуала и ссылки на источник. Модель получает весь читаемый текст с метками
блоков и фрагментов, факты графа и до 32 выдержек для навигации. Сослаться
можно на любую метку, включая фрагменты за пределами выборки выдержек.
PDF с текстовым слоем передаёт абзацы и таблицы в порядке расположения на
странице. Короткие строки одного абзаца объединяются, номера страниц
сохраняются в ссылках на источник.

При достаточном материале план распределяет темы по содержательным слайдам.
Для каждой темы промпт просит 2–4 конкретные детали в видимом тексте,
включая существенные условия и статус решений. Для диаграмм и карточек
промпт просит пояснить числовой ряд и сохранить контекст сравнения.

ML проверяет наличие опоры у содержательных слайдов и разрешает только
идентификаторы из отправленного набора. Проверка действует и после объединения
слайдов. Ссылки привязываются к исходным блокам и, где применимо, к страницам,
строкам таблиц или диапазонам символов. Проверка адреса позволяет найти опору,
а точность пересказа требует отдельной проверки.

Внутренний `DeckPlan` привязан к ID итоговых слайдов. Если соседние блоки
объединяются, итоговый слайд сохраняет обе части плана. Для добавленных обложки
и финала приложение создаёт пункты плана и переносит ссылки из блока, взятого
для итогового резюме. Пока план используется внутри ML и доступен следующему
шагу композиции. Форматы сохранённой презентации и командной правки прежние.
Режим сравнений использует свой ответ с проверяемыми строками таблиц.

Проверка 20 ноября 2026 года прошла на синтетическом PDF с двумя страницами
и четырьмя строками сравнений. За один успешный запрос GigaChat-3-Ultra вернул
6 слайдов и план с 12 ссылками. Проверены адреса ссылок, соответствие плана ID
слайдов и открытие итогового PPTX в PowerPoint. Прогон занял 24,16 с и использовал
соединение SDK, подтверждённое авторизованным запросом метаданных после таймаутов.

При чтении слайдов восстановление записей журнала оказалось передано как
добавление событий.

Повторный живой прогон 21 ноября на том же PDF дал 6 слайдов за один вызов
GigaChat-3-Ultra. В видимом тексте получилось 225 слов против 137 в первом
живом прогоне. Подписи диаграммы и заметки в счёт не входят. На слайдах
сохранились методика подсчёта, оба периода замера ожидания, отсутствие
замера по телефону и восстановление 11 записей. В PPTX сверены значения
редактируемой диаграммы. Условие допуска без записи на Выездной площадке
модель опустила.

Приложение строит диаграмму, когда `DeckPlan` запрашивает `comparison` и
ссылается на несколько сопоставимых строк одной таблицы. Для `metric`
берутся два значения из одной проверенной строки с показателем, группой
и периодами в подписях. Если поле отсутствует в сохранённом ответе, используется
`text`. Режим сравнений также строит
диаграмму для одной проверенной строки. Смешанные единицы, неоднозначные
разделители, отрицательные значения и данные вне диапазона сохраняются в
текстовом виде. Для пары метрик и ограничений доступны отдельные композиции.

Для текстовых слайдов план может выбрать `lead` для тезиса с пояснениями,
`blocks` для равноправных смысловых блоков или `steps` для описанной в
источнике последовательности. Эти композиции оформляют строки `body`,
не добавляя факты. Превью и PPTX используют обычную компоновку, когда
выбранная композиция не помещает текст.

Для явной иерархии можно выбрать `tree`. Сервер сравнивает строки, уровни
и порядок с непрерывным фрагментом источника. Если модель выбрала `text`
и записала иерархию сплошным абзацем, сервер также может восстановить её
из источника. Для этого весь текст слайда должен совпасть с одним
исходным деревом по словам, числам и порядку, а план должен ссылаться
на общий объект и все названия групп. При расхождении с источником или
переполнении карточек применяется обычная раскладка. Группы оформляются
колонками. Карточки и текст экспортируются отдельными объектами PowerPoint.

На учебном PDF с описанием доступа к фондам один живой ответ GigaChat
передал дерево обычным текстом. При повторной обработке сохранённого
ответа сервер восстановил три ветки и шесть исходных пунктов. Остальные
три слайда сохранили свои макеты.

При живой проверке этих вариантов 21 ноября GigaChat-3-Ultra за один
вызов вернул 6 слайдов с 145 словами видимого текста. Модель выбрала
`comparison` для таблицы и `text` для остальных слайдов. Варианты
`lead`, `blocks` и `steps` проверены на сохранённых и подготовленных
ответах. На слайде об ограничениях модель ошибочно назвала восстановление
11 записей добавлением 11 завершённых занятий. Проверка проводилась от
импорта PDF до PPTX без очереди и БД.
В автоматической генерации их подключение остаётся следующим этапом.

Для любой длины источника JSON Schema ограничивает число слайдов значением
`slideCount`, включая титульный и заключительный. На коротком источнике остаётся
лимит `min(slideCount, 4)`. Инструкция `generation-wire-v1` просит точное число при
достаточном материале и разрешает меньше, если материала мало. После добавления
пропущенных краевых слайдов и существующей нормализации итог проверяется повторно:
при превышении у длинного источника подбирается разбиение на соседние
содержательные блоки, сохраняющее их порядок и укладывающееся в бюджет.
При генерации v4 поле `review_sections` передаёт короткие дословные
абзацы из явно названных разделов о наблюдениях, ограничениях и планах.
Это помогает сохранить единицы измерения рядом с соответствующим результатом
или целевым показателем. Длинные содержательные подписи внутренних
разделителей приводятся к текстовому макету с сохранением текста и заметок.
Весь видимый текст, включая заголовки и подписи колонок,
переносится дословно в text; заметки объединяются. Обложка и заключение не
объединяются. Лимиты объединённого блока — 800 кодовых единиц UTF-16 видимого
текста и 10 000 для заметок. Если подходящей пары нет, ответ отклоняется как
невалидный, а не публикуется как N+1.
Слайды не обрезаются, повторного платного запроса нет. Строгое ограничение не
гарантирует успешный ответ модели на любом исходнике — требуется живая приёмка.

Название обложки совпадает с названием документа: используется введённое
пользователем непустое название, иначе — название из ответа модели по докладу.
Отдельно просить титульный слайд не требуется. Инструкция запрещает заменять тему
названием первого раздела и помещать абзац о проблеме в мелкую подпись обложки.
Подзаголовок, краткая подпись и заметки сохраняются; `revise` не меняется.
Профиль кэша приёмки учитывает полный промпт, включая правила структуры, и новую
версию нормализации. Старые результаты не подтверждают исправленное поведение.

Заключение генерации должно иметь непустой `subtitle`: краткий итог с существенной
оговоркой и, только если он есть в исходнике, следующий шаг. Это требование есть
в инструкции и схеме ответа модели. Если модель пропустила заключение либо вернула
только заголовок, берётся целый видимый блок из уже сгенерированного содержания
до объединения слайдов, не длиннее 400 единиц UTF-16. Его заголовок переносится
в заключение или включается в текст, чтобы не потерять область утверждения.
Пустой повтор названия документа заменяется названием этого блока. Новые факты,
универсальные русские фразы и обрезка текста не добавляются. Если безопасного
блока нет, ответ отклоняется; повторного запроса нет. Уже содержательное заключение
и выборочные правки не меняются. Извлечённый повтор не восстанавливает сведения,
которые модель не включила в свой ответ: смысловая приёмка по исходнику обязательна.

Модель возвращает кандидат документа. Модуль валидирует результат и при отсутствии
краевых макетов добавляет title/closing с уже полученным `document.title`.
Заключение не содержит жёстко заданной русской фразы, поэтому английский исходник
не получает русское заключение от нормализатора.

Внутренний заголовочный title/section перед содержательным слайдом без заголовка
может быть объединён с ним в text. Заголовок, подпись, подзаголовок, подписи
колонок, все строки и заметки сохраняются. Объединение выполняется только при
читаемом объёме; длинная пара остаётся без изменения. Для правки оно не применяется.

В профилях v3–v7 источник короче 1000 Python Unicode code points получает целевой
объём min(slideCount, 4). Это эвристика, не правило внешнего контракта. Если после
добавления краевых слайдов объём превышен, соседние короткие разделы упаковываются
дословно в один/два text-слайда: body не более 800 символов, заметки сохраняются,
итог снова проходит строгую проверку UTF-16 и размера. Если упаковка не помещается,
ответ отклоняется; текст не обрезается и новый платный запрос не запускается.
Часть заголовков при такой упаковке может повториться в body — известная
косметическая особенность в пользу сохранения строк.

## Выборочная и общая правка

Внутренний ответ: `{"status":"applied","document":...}` либо
`{"status":"unsupported","document":null}`. Эта оболочка не возвращается backend.

При явных целях модель получает полный контекст, но возвращает только выбранные
замены в document.slides. Схема ограничивает их число и допустимые ID. Код проверяет
точное множество ID, затем подставляет замены в замороженную исходную копию.
Публичный результат всегда полный, с исходным порядком и количеством. Невыбранные
слайды целиком и общий title сохраняются, даже если выбраны все номера.
Списки целей и исходный документ передаются провайдеру копиями; проверка результата
использует неизменяемый снимок целей. Мутация payload не расширяет разрешённую область.

Без явных целей модель возвращает все слайды; ID, порядок и количество проверяются,
а содержимое и общий title могут меняться. Входной объект не изменяется.

`capabilities.py` до запроса отклоняет распознанные явные RU/EN команды добавления,
удаления и перемещения слайдов. Проверены отрицания, цитаты и правки slide title/body.
Это консервативная проверка, а не универсальный интерпретатор произвольного языка.
Неизвестные формулировки ещё зависят от модели и проверки результата. Отказ →
NotImplementedError; невалидный кандидат → ValueError, без фиктивного успеха.

## Версии промптов и граница провайдера

`prompts.py` и `prompt_templates/` хранят версии. Старый v1 сохранён точно,
его сообщения проверяются хешами. v2 подробнее задаёт ограничения; v3 добавляет
короткий бюджет; v4 сохраняет адресатов, условия и степень уверенности.

v5–v7 оставлены как явно выбираемые исследовательские варианты, не рекомендуются
основными: v5 проверяет покрытие извлечённых заголовков, v6 — самостоятельный короткий
промпт, v7 — дословные source_quotes перед пересказом. В v7 буквальное наличие цитат
проверяется, внутреннее поле удаляется, фрагменты добавляются в notes. Это НЕ проверка
логического следования: реальная цитата может сопровождать неверный пересказ.
Содержательные слайды требуют цитату, title/closing допускают пустой список.
После последующих правок старые цитаты также требуют сверки. Провалы экспериментов
зафиксированы в отчёте; увеличение номера не означает улучшение качества.

`transport.request_document` вызывает JsonProvider. Единственный адаптер сейчас —
`providers/gigachat.py`, официальный SDK, ленивый клиент, TLS, `max_retries=0`.
Незнакомый `PM_ML_PROVIDER` даёт NotImplementedError. Другие провайдеры не получают
этот ключ и не включаются автоматически. Интерфейс подготовлен для расширения,
но смена провайдера не реализована и в текущую работу не входит.

## Экономная проверка

14 вымышленных случаев, включая девять разноплановых, перечислены в
[ML_SYNTHETIC_CASES.md](ML_SYNTHETIC_CASES.md). Ожидаемые факты и недопустимые выводы
хранятся отдельно от text и не передаются модели.

Из `backend`, без обращения к модели:

```bash
uv run --locked python -m tools.ml_acceptance --case finance-plan-vs-actual --output /private/review
```

Без сохранённого ответа будет `not_run`, а не успешная приёмка. Для осознанного
нового вызова добавляются `--live` и явный `--case`. `--save-candidates` сохраняет
сырой ответ до проверки, только если все выбранные случаи помечены synthetic=true.
Файлы содержат текст, храните их приватно. Кандидат можно повторно подставлять
в локальные проверки нормализатора без провайдера. В server logs он не попадает.

Перед вызовом пишется статус started. Неуспешная/прерванная попытка блокирует
неявный повтор в том же каталоге. Изменение профиля или входа также не маскируется
перезаписью результата. Новый каталог выбирается намеренно после диагностики.
Сохраняются модель, scope, версия/хеш промпта и политики нормализации. Ошибки
описываются классами/флагами, без текстов исключений и ключей.

Последняя проверка: 116 тестов прошли в шести ML/adapter/runner-файлах, Ruff прошёл.
Это целевой набор, не повтор полного backend/DB-интеграционного набора.
Сквозной браузерный путь v4 + wire-v3 прошёл за 17,56 с в одном синтетическом случае.
Девять выбранных документов экспортированы, 59 слайдов проверены по XML и рендерам
LibreOffice; одобрение пользователем ещё ожидается. Повторяемость качества,
нативный PowerPoint и реальные материалы требуют отдельной приёмки.

SDK обновляет токены, но интервальные ConnectError/SSLEOFError ранее встречались;
точная причина не установлена. Успешные последующие запросы не доказывают устранение
сетевой проблемы. До deadline оставляется запас 10 с; завершение локального процесса
не гарантирует отмену уже отправленного запроса у провайдера.

### Проверка текста в экспортированном PPTX

В локальном файле случаев укажите `id`, `slideCount` и текстовые фрагменты
в `anchors` и `forbidden_fragments`. В каталоге презентаций каждому случаю
соответствует файл `<id>.pptx`. Из `backend` запустите:

```bash
uv run --locked python -m tools.pptx_acceptance --cases /private/cases.json --pptx-dir /private/decks --output /private/pptx-review.json
```

Отчёт показывает номера слайдов с каждым совпадением, пропущенные фрагменты и
отклонение от ожидаемого числа слайдов. Код возврата 1 сигнализирует о расхождении
или об ошибке чтения хотя бы в одном случае. Слайды без текста перечисляются
для ручного просмотра, поскольку могут содержать диаграммы или изображения.
`slide_count_mode: "maximum"` применяйте, когда `slideCount` задаёт верхнюю
границу. Меньшее число слайдов остаётся видно в отчёте.
Данные диаграмм, заметки и обрезку текста проверяйте отдельно. Храните отчёты по
реальным материалам локально, поскольку в них записываются контрольные фрагменты.

### Отслеживание факта до PPTX

Добавьте к случаю массив `facts`. У каждого факта есть уникальный `id`,
фрагмент `source` в извлечённом документе и необязательный список допустимых
формулировок `slide_phrases` для JSON и PPTX. Если список опущен, используется
исходная формулировка. Например:

```json
{
  "id": "control-group",
  "source": "В пилоте не было контрольной группы",
  "slide_phrases": ["Пилот без контрольной группы", "Контрольная группа отсутствовала"]
}
```

Сохраните соответствующие одному запуску снимки `<id>.json` в двух каталогах.
В первом хранится извлечённый `SourceDocument` с массивом `blocks`, во втором —
презентация с массивом `slides` перед экспортом. Из `backend` запустите:

```bash
uv run --locked python -m tools.pptx_acceptance --cases /private/cases.json --pptx-dir /private/decks --source-dir /private/source --document-dir /private/document --output /private/fact-trace.json
```

Отчёт указывает ID блоков, номера слайдов и первый снимок без совпадения
(`source`, `document` или `pptx`). Отсутствующий либо повреждённый снимок
даёт ошибку входных данных с указанием этапа. Проверка ищет указанные фразы
без учёта регистра и различий в пробелах. Для смысловой сверки чисел,
единиц, оговорок и перефразирования по-прежнему нужен исходный контекст.
Укажите `"match": "exact"` для коротких названий, которые не должны
совпадать с частью другой подписи.
Для оговорки, которую аудитория должна увидеть до финала, задайте
`"placement": "interior"`. Совпадения на обложке и финальном слайде
учитываются как присутствие фразы и отдельно отмечаются как ошибка размещения.
Укажите `slide_context`, если число должно находиться в одном абзаце с группой,
показателем или единицей. Из списка допустимых формулировок достаточно одной.
Отчёт отдельно показывает слайды, на которых число нашлось без этого контекста.

В том же случае можно задать `charts`. Каждая проверка связывает 1-based
номер `slide` с блоком таблицы `source_block`, номерами строк `rows` и
двумя сравниваемыми периодами `periods`. Нумерация строк включает заголовки
таблицы. Пример поля случая:

```json
{
  "charts": [
    {"slide": 2, "source_block": "p1-table-1", "rows": [3, 4], "periods": ["2024", "2025"]}
  ]
}
```

Проверка сверяет группы, периоды, значения и единицу в модели слайда и в
привязанной к нему диаграмме. Отдельно проверяет наличие подписей, знак процента
и точность отображения. `allow_table: true` разрешает редактируемую таблицу
с теми же группами, периодами, числами и единицами.
Добавьте `chart_coverage` с парами `source_block` и `periods`, когда
презентация должна охватывать все распознанные строки этой таблицы. Отчёт
отдельно перечисляет строки без слайда и строки с расхождениями.
Укажите `"geometry": true`, чтобы проверить размеры нативных таблиц и диаграмм
в экспортированном файле. Проверка сравнивает рамку таблицы с размерами
её строк и колонок и отмечает выход графического объекта за пределы слайда.
В отчёте указаны номер слайда, тип объекта и размеры в EMU.

Для сравнения версий добавьте `--baseline-pptx-dir` к той же команде.
Если в сценариях есть факты или диаграммы, укажите также
`--baseline-document-dir`. Обе версии используют одни и те же сценарии,
идентификаторы файлов и извлечённые источники из `--source-dir`.

Поле `comparison` показывает изменения по фактам с указанием первого этапа,
на котором нарушилось требование, появившиеся и исчезнувшие запрещённые
фрагменты и число геометрических нарушений до и после, если эта проверка
включена. `improvement` означает, что факт прошёл все этапы, а `regression`
означает, что раньше он их проходил. `changed` показывает смену этапа или
типа нарушения. Код завершения равен 1, если новая версия требует проверки
или одну из версий не удалось прочитать.

Планирование v4 передаёт вводные условия отдельным разделом
`review_sections.context`. Рекомендации доступны в `review_sections.proposed`.
В `review_sections.method_changes` попадают дословные оговорки о смене сбора
данных, если источник прямо описывает её последствия для сравнения.
`review_sections.period_comparisons` содержит выдержки с несколькими годами
и значениями. Когда сравнение начинается со ссылки на предыдущую фразу,
пакет сохраняет и эту фразу. Коды таблиц остаются доступны как ссылки на
источник и сами по себе не делают фрагмент числовой цитатой.
В `source_glossary` попадают дословные раскрытия в пределах 12 сокращений
с ID блока и номером страницы, если он есть. Неоднозначные раскрытия пропускаются.

### Диагностика макетов

Из каталога `frontend` запустите аудит сцен по сохранённым документам:

```bash
npm exec -- vite-node scripts/audit-layout.ts --output /private/layout-report.json /private/deck.json
```

Добавьте `--pptx-dir /private/decks`, чтобы вместе с отчётом получить PPTX из
тех же снимков. Имя файла JSON определяет имя презентации в каталоге экспорта.

Отчёт содержит оценку обрезки текста, уменьшение шрифта, выход за пределы
слайда и пересечения элементов. Для внутренних слайдов он показывает долю
высоты содержательной области, занятую текстом, таблицами и иллюстрациями.
Отчёт использует геометрию и оценку высоты текста редактора. Финальный вид
слайда проверяется по рендеру PowerPoint.
