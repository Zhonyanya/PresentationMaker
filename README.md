# PresentationMaker

Приложение для создания презентаций по тексту доклада: ввод текста → генерация → просмотр и правки → **редактируемый PPTX**.

Фронтенд и серверная инфраструктура реализованы. **Реальная модель пока не подключена**: для неё подготовлен интерфейс Python-модуля; системные промпты, провайдер и качество содержания остаются задачей ML.

| Режим | Генерация и правки | Хранение и доступ |
|---|---|---|
| `VITE_API_MODE=mock` (по умолчанию) | Эвристики в браузере, ручной редактор | Один локальный черновик, без входа и backend |
| `VITE_API_MODE=http` | Асинхронные задания backend; правки текстовыми командами | Вход по серверной сессии, текущие документы в PostgreSQL |

В HTTP-режиме `PM_ML_ADAPTER=fixture` — отдельная **серверная тестовая заглушка**, а не настоящий ML и не браузерный mock. Она выдаёт шесть фиксированных слайдов независимо от доклада.

Документация:

- **[Контракт подключения ML](ML_CONTRACT.md)** — обязательный интерфейс, формат данных и ограничения совместимости.
- **Backend:** [архитектура](#архитектура-бэкенда), [тесты](#тесты), [production-эксплуатация](#production-эксплуатация).
- **OpenAPI** запущенного backend: `/docs`, `/openapi.json`; префикс API — `/api/v1`.

## Быстрый старт

### Полный стенд одной командой (рекомендуется)

Нужны **Docker Engine / Docker Desktop и Docker Compose v2**. Из корня репозитория:

```bash
docker compose up --build -d --wait --wait-timeout 180
```

Откройте **http://localhost:8080**, создайте аккаунт (пароль 15–128 символов), вставьте доклад и скачайте PPTX. OpenAPI: http://localhost:8080/docs. На первой сборке нужен интернет для загрузки образов и зависимостей; Node.js, Python, PostgreSQL и Redis на хост устанавливать не нужно. Копировать `.env` тоже не нужно.

Compose сам создаёт PostgreSQL/Redis, применяет миграции **до** API и worker, запускает отдельные ML/maintenance-worker и один Beat. Nginx отдаёт собранный frontend и проксирует `/api` с того же origin. API и оба worker имеют health-checks; публикация наружу — только `127.0.0.1:8080`. Проверка:

```bash
docker compose ps -a
curl --fail http://localhost:8080/api/v1/health/ready
docker compose logs --tail=100 api worker maintenance beat
docker compose down
```

`migrate` с `Exited (0)` — норма. `down` сохраняет данные в именованных томах; повторный `up` их использует. **Не добавляйте `--volumes` / `-v`, если данные нужны.** После изменения кода повторите команду с `--build`. Если порт занят: `PM_WEB_PORT=8081 docker compose up --build -d --wait --wait-timeout 180`, затем http://localhost:8081; используйте тот же `PM_WEB_PORT` в дальнейших командах Compose.

**Это локальный development-стенд с фиксированной fixture, не настоящий ИИ и не production.** Демонстрационные пароли, открытая регистрация и HTTP намеренно ограничены локальным доступом. Не выставляйте стенд в интернет. Для production нужны реальный ML-модуль в backend-образе, HTTPS, секреты и настройки из [раздела эксплуатации](#production-эксплуатация); одного `PM_ENVIRONMENT=production` недостаточно.

**Если установлен Podman вместо Docker** (проверено на rootless Podman 5.8.9), нужен Compose-провайдер. При установленном `uv`:

```bash
uvx --from podman-compose==1.6.0 podman-compose up --build -d
curl --fail http://localhost:8080/api/v1/health/ready
uvx --from podman-compose==1.6.0 podman-compose down
```

У этого провайдера нет флага Docker Compose `--wait`: порядок запуска задают `depends_on` и health-checks, а результат проверяйте через ready и `podman ps -a`. Не смешивайте команды Docker и Podman для одного стенда.

### Автономная демонстрация

Рекомендуется **Node.js 24 LTS** (`nvm use`, если установлен nvm); также поддерживаются Node 20.19+ и 22.12+. Версии ограничены в `frontend/package.json`, выбранная LTS — в `frontend/.nvmrc`. Все команды фронтенда выполняются из `frontend/`:

```bash
cd frontend
npm ci             # 1. зависимости по lock-файлу
VITE_API_MODE=mock npm run dev  # 2. запуск → http://localhost:5173
npm run build      # 3. production-сборка → папка dist/
npm run preview    #    посмотреть собранную версию
npm test           #    тесты (Vitest)
npm run typecheck  #    проверка типов
```

`frontend/dist/` — обычная статика. `npm run preview` — локальная проверка сборки, не production-сервер. Команды с `NAME=value` показаны для bash/zsh; в PowerShell используйте `$env:NAME="value"` перед командой. `VITE_*` из старого `.env.local` могут менять режим сборки: проверьте их при переходе между mock и HTTP.

### Серверный сценарий без Docker (разработка)

Нужны Python 3.13–3.14 (проверен 3.13), `uv`, PostgreSQL и Redis. Из `backend/` установите зависимости и настройте окружение:

```bash
uv sync --locked --python 3.13
cp -n .env.example .env
```

Создайте отдельную БД `presentation_maker`, настройте `PM_DATABASE_URL`, `PM_REDIS_URL` и `PM_ALLOWED_ORIGINS` в `backend/.env`. Затем выполните миграции и запустите **каждый сервер отдельной командой в своём терминале**, также из `backend/`:

```bash
uv run --locked alembic upgrade head
uv run --locked uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
uv run --locked celery -A app.worker:celery worker --queues=celery --hostname=ml@%h --concurrency=1 --loglevel=INFO
uv run --locked celery -A app.worker:celery worker --queues=pm.maintenance --hostname=maintenance@%h --concurrency=1 --loglevel=INFO
uv run --locked celery -A app.worker:celery beat --loglevel=INFO --schedule=./celerybeat-schedule
```

Нужен один Beat; отдельный maintenance-worker обязателен, чтобы обслуживание не ждало окончания ML. Файл расписания создаётся в `backend/` и исключён из Git. Для полного backend на хосте нужен Linux (watchdog ML использует POSIX); на macOS/Windows используйте Docker.

Из `frontend/`:

```bash
npm ci
VITE_API_MODE=http VITE_DEV_PROXY_TARGET=http://127.0.0.1:8000 npm run dev
```

Открывайте **http://localhost:5173**: этот Origin разрешён в примере backend. `http://127.0.0.1:5173` — другой Origin. В `backend/.env.example` явно включён `fixture`; для реального модуля нужны `PM_ML_ADAPTER=module` и `PM_ML_MODULE=presentation_ml`. Production запрещает fixture. Интерфейс — в [ML-контракте](ML_CONTRACT.md).

## Пользовательский сценарий

1. **Создание.** Название (необязательно), текст доклада или плана, примерное число слайдов. Текст можно вставить, загрузить из `.txt`/`.md`/`.docx` или перетащить файл в поле. Есть три демо-примера. Файлы разбираются в браузере: backend получает текст, не upload.
2. **Генерация.** В mock этапы имитируются и помечены как «Демо». В HTTP сначала нужен вход/регистрация; сервер принимает задание, интерфейс опрашивает его статус без выдуманных процентов. Ошибка задания не уничтожает предыдущий успешный документ.
3. **Правки.** В HTTP — просмотр 16:9, выбор слайдов и текстовые команды ко всей презентации либо указанным номерам. Ручное изменение полей, drag-and-drop, добавление и удаление скрыты. ML-правка обязана сохранять ID, число и порядок слайдов. В mock остаётся ручной редактор с инспектором, перестановкой, дублированием, удалением и автосохранением в браузере.
4. **Экспорт.** «Скачать PPTX» → имя файла, заметки докладчика, проверка перегруженных слайдов → файл.

В HTTP остановка ожидания, закрытие вкладки и logout **не отменяют серверную задачу**. После перезагрузки восстанавливаются текущий серверный документ и известная активная задача, но не приватный текст формы. В localStorage хранятся только ссылки на presentation/job, привязанные к пользователю; архива и списка работ в UI нет.

Горячие клавиши **ручного mock-редактора**: `↑/↓` — соседний слайд, `Alt+↑/↓` — переместить слайд, `Delete` — удалить слайд (когда фокус в списке слайдов), `Пробел` на миниатюре — взять и перенести стрелками. В списке пунктов: `Enter` — новый пункт, `Backspace` в пустом — удалить, `Alt+↑/↓` — порядок.

## Дизайн интерфейса

Редакционный стиль: тёплая бумажная основа, чернильный чёрный, один терракотовый акцент, линии в 1 px, без градиентов и «стекла».

- Шрифты: **Noto Serif Display** (заголовки) и **Inter Tight** (интерфейс), оба с кириллицей, подключаются локально через `@fontsource` — работают без доступа к Google Fonts.
- Токены цветов, радиусов и теней — `frontend/src/index.css`. Общие параметры анимаций — `frontend/src/components/app/motion.ts` (библиотека `motion`).
- Анимации учитывают системную настройку «Уменьшить движение» (`MotionConfig reducedMotion="user"`).
- Дизайн интерфейса и оформление слайдов — разные системы: слайды строго следуют `presentation-theme.ts`.

## Демонстрационный режим

Включён по умолчанию (`VITE_API_MODE=mock`).

- Генератор: `frontend/src/api/mock/mock-generator.ts` и `frontend/src/api/mock/text-analysis.ts`. Он выделяет заголовки (`#`, нумерация, короткие строки без точки, ЗАГЛАВНЫЕ), абзацы, списки и пары вида «Проблемы: … / Решения: …», раскладывает их по макетам и подгоняет число слайдов к запрошенному. Формулировки берутся из исходного текста, полный текст блока уходит в заметки докладчика. **Это не ИИ** — интерфейс честно помечает режим бейджем «Демо-режим».
- Ответ mock-генератора проходит ту же Zod-валидацию, что и ответ сервера.
- Проверить экран ошибки: откройте `http://localhost:5173/?mockFailEvery=1` — каждая генерация завершится ошибкой сервера.

## Архитектура бэкенда

Backend — модульное FastAPI-приложение с отдельными процессами выполнения заданий, не синхронная обёртка над LLM.

```text
React: App → ServerApp → server-api.ts
             │ cookie + CSRF + Idempotency-Key
             ▼
FastAPI /api/v1 ───────────────► PostgreSQL (источник истины)
  auth / presentations / jobs     users, sessions, presentations, jobs
             │ после commit: только job_id
             ▼
Redis (брокер Celery + rate limits)
  ├─ очередь celery ───────────► ML-worker
  │                              └─ supervisor → Python runner → ML-модуль
  │                                 JSON → валидация → атомарная запись в PostgreSQL
  └─ очередь pm.maintenance ◄── Celery Beat (каждые 15 с)
             └────────────────► maintenance-worker → восстановление/очистка в БД

Браузер: polling Job → GET текущего документа → SlideScene → превью / PPTX
```

### Модули и ответственность

| Модуль | Назначение |
|---|---|
| `backend/app/main.py` | Сборка ASGI, CORS/Host, пределы HTTP, безопасные ошибки, request_id и health-checks |
| `backend/app/auth/service.py` | Аккаунты, Argon2id, серверные сессии, CSRF/Origin и rate limiting |
| `backend/app/presentations/routes.py`, `schemas.py` | HTTP-маршруты, валидация запросов и данных шести макетов |
| `backend/app/jobs/service.py` | Приём задания, проверка токена документа, идемпотентность, квоты и входной снимок |
| `backend/app/worker.py` | Celery, захват задания, heartbeat, вызов ML, публикация результата и maintenance |
| `backend/app/ml/adapter.py`, `runner.py` | Подключение fixture/реального модуля, проверка результата и области правки, процессный JSON-протокол |
| `backend/app/core/process.py`, `supervisor.py`, `readiness.py` | Ограниченный обмен с subprocess, watchdog и проверка импорта ML |
| `backend/app/db/`, `backend/alembic/` | ORM, отдельные async/sync-пулы API/worker и миграции PostgreSQL |

### Данные и выполнение задания

- `users` — аккаунты и хеши паролей; `sessions` — серверные сессии, хеш cookie-токена и CSRF-токен.
- `presentations` — **только текущий** JSON-документ каждой презентации, исходный текст, желаемое/фактическое число слайдов и случайный `document_token`. Несколько презентаций у аккаунта допустимы; истории версий нет.
- `jobs` — статус, deadline, ключ идемпотентности, хеш запроса и временный входной снимок. После завершения снимок очищается, служебные метаданные остаются. Job не хранит архивную копию результата.

1. API проверяет владельца, вход, лимиты и актуальность `base_document_token`, создаёт Job и фиксирует транзакцию PostgreSQL. Приём сериализован advisory-lock; частичный UNIQUE допускает лишь одно активное задание на презентацию.
2. После commit API пытается отправить `job_id` в Redis. Сбой публикации не теряет принятое задание: maintenance повторно доставляет оставшиеся `queued` записи.
3. Worker атомарно захватывает Job со случайным `attempt_token`. Повторная доставка уже захваченной задачи не должна повторять ML. Модель вызывается вне транзакции БД, один раз через отдельный Python-процесс.
4. Результат проходит валидацию схемы и инвариантов правки. Публикация повторно проверяет право попытки, deadline и базовый токен; только успех атомарно заменяет документ, токен, исходный текст и счётчики. При ошибке старый документ остаётся доступным.
5. Клиент опрашивает Job и отдельно забирает текущий документ. `output_document_token` позволяет понять, остаётся ли результат задания текущим; это не ссылка на сохранённую версию.

Статусы: `queued → running → succeeded / failed / timed_out` (ожидающее задание тоже может завершиться ошибкой/таймаутом). Фазы: `waiting`, `ml`, `validation`, `saving`, `done` — не проценты готовности.

По умолчанию **1500 секунд от принятия**, включая очередь и выполнение, heartbeat — 15 секунд, обнаружение потерянного worker — 120 секунд. Maintenance обрабатывает дедлайны и потерянные задачи, очищает снимки завершённых jobs и истёкшие сессии. Потерянный `running` не перезапускает платный вызов. Гарантии exactly-once для внешнего провайдера нет; Celery result backend не используется, истина — Job в PostgreSQL.

### Границы безопасности и эксплуатации

Доступ — HttpOnly-cookie, не JWT; изменяющие запросы требуют доверенный Origin и `X-CSRF-Token`. В production cookie Secure, регистрация по умолчанию закрыта. Есть Redis rate limits и квоты задач в PostgreSQL; чужие presentation/job возвращают 404. Ключи модели допустимы только в серверном окружении, не в `VITE_*`.

`GET /api/v1/health/live` проверяет HTTP-процесс; `health/ready` — БД, Redis и импортируемый callable `generate`, но **не** качество модели, `revise`, доступность GPU или работоспособность очередей. Импорт ML проверяется в subprocess (5 с, кеш 30 с), поэтому загрузка весов на уровне импорта нежелательна.

Watchdog завершает группу ML-процесса по deadline/потере worker. Это **не песочница**: лимиты памяти/GPU, сетевой доступ, изоляция секретов, HTTPS, резервное копирование и мониторинг настраиваются при развёртывании. `compose.yaml` и Dockerfiles обеспечивают локальный стенд, но не production-оркестрацию.

Основные ограничения backend по умолчанию (настройки — `backend/app/core/config.py`, переменные с префиксом `PM_`):

| Область | Ограничения |
|---|---|
| Аккаунты | ASCII-логин 3–64, `[a-zA-Z0-9_.-]`, без учёта регистра; пароль 15–128 без trim/нормализации, Argon2id |
| Сессии | В БД SHA-256 cookie-токена; 7 суток абсолютно / 24 часа неактивности; предварительная сессия 20 минут. Cookie HttpOnly, Lax, без Domain: `pm-dev-session` локально, `__Host-session; Secure` в production |
| HTTP | Тело ≤2 000 000 байт, загрузка ≤30 с, до 100 одновременно принятых запросов на API-процесс до конца обработки. Превышения: 413 / 408 / 503 |
| Вход/регистрация | Redis rate limits по IP, логину (30 попыток за 15 минут) и сервису (300/мин); дорогие проверки пароля ограничены по конкуренции, занятые слоты дают 429 без ожидания |
| Активные задания | 2 на пользователя, 100 на сервис; Celery prefetch=1 |
| Суточные задания | 20 на пользователя / 500 на сервис за скользящие 24 часа, включая ошибки; идемпотентные повторы не расходуют бюджет |
| Накопительные квоты | Презентации: 100 на пользователя / 5000 всего; jobs: 5000 / 100 000; аккаунты: 10 000; регистрации: 50 попыток/сутки. Квоты ограничивают рост, не удаляют данные |

При отсутствии/истечении сессии защищённые POST и logout возвращают 401 до проверки CSRF; действующая сессия с неверным Origin/CSRF — 403. Login/register требуют CSRF предварительной сессии. Ответы — `no-store`, ошибки не содержат приватный ввод; NUL отклоняется до записи в PostgreSQL.

Снимки входов завершённых jobs очищаются, метаданные/хеш запроса остаются для polling и идемпотентности. Maintenance дополнительно очищает до 200 старых снимков за проход; текущие документы и исходники автоматически не удаляются. Очистка не удаляет данные из backup/WAL/MVCC. Celery SUCCESS не подтверждает успех генерации: проверять нужно Job в PostgreSQL/API.

## HTTP API и подключение фронтенда

В `frontend/.env`/`frontend/.env.local`:

```bash
VITE_API_MODE=http
VITE_API_BASE_URL=https://api.example.ru   # пусто — тот же домен
VITE_DEV_PROXY_TARGET=http://127.0.0.1:8000 # только для npm run dev: прокси /api → бэкенд
```

`VITE_*` вшиваются при сборке. Production обычно отдаёт `frontend/dist/` и `/api` с одного origin. При отдельном API-домене нужны явный CORS с credentials и проверка cookie в целевом браузере.

Текущий `server-api.ts` ограничивает **отдельный HTTP-запрос 20 секундами**, а не держит соединение на всю генерацию. Polling — каждые 2,5 с (10 с в скрытой вкладке), без общего клиентского таймера на 25 минут. `VITE_API_TIMEOUT_MS` относится только к старому синхронному клиенту и **не используется ServerApp**; серверный бюджет задаётся `PM_JOB_DEADLINE_SECONDS` (не более 1500 с).

Все маршруты ниже имеют префикс **`/api/v1`**:

| Метод и путь | Назначение |
|---|---|
| `GET /auth/csrf` | Предварительная сессия и `csrf_token` |
| `POST /auth/register`, `/auth/login` | `{login,password}` → `{user,csrf_token}`, ротация сессии |
| `GET /auth/me`, `POST /auth/logout` | Текущий пользователь / отзыв сессии |
| `POST /presentations` | `{text,title?,slideCount}` → **202** `{presentation_id,job_id,status_url}` |
| `GET /jobs/{id}` | Статус, фаза, безопасная ошибка и `output_document_token` |
| `GET /presentations/{id}` | `{presentation_id,document,document_token,requested_slide_count,slide_count,active_job}` |
| `POST /presentations/{id}/generations` | Полная перегенерация: `{text,title?,slideCount,base_document_token?}` |
| `POST /presentations/{id}/revisions` | Команда: `{instruction,base_document_token,target_slide_numbers?}` |

Все три POST генерации/правки требуют `Idempotency-Key` (1–128 печатных ASCII-символов без пробелов), cookie, CSRF и Origin. Одинаковый ключ и запрос возвращают уже принятое задание; другое тело/операция/цель с тем же ключом — 409. После терминальной ошибки новая попытка требует новый ключ. Токен обязателен для правки и перегенерации существующего документа; до первого успеха перегенерация возможна без него.

Вход генерации: `text` после trim 100–60 000 символов, `title` до 200, обязательный целый `slideCount` 3–20. Команда: 1–10 000 символов; номера целей — уникальные, с 1, в пределах документа. Желаемое число слайдов не обязано совпадать с фактическим: документ содержит 1–60 слайдов. Макеты — `title`, `text`, `bullets`, `two-column`, `section`, `closing`.

Ошибки HTTP: `{"error":{"code":"…","message":"…"},"request_id":"…"}`. Ошибка выполнения ML появляется в Job, а не превращает ранее принятый 202 в 5xx. Точные схемы — в OpenAPI и [ML-контракте](ML_CONTRACT.md). Маршрутов `/api/generate`, серверного экспорта и отмены задачи в текущем API **нет**.

### Как устроено превью и экспорт

```
Slide (данные) ──► определение макета.buildScene() ──► SlideScene ──┬──► SlideRenderer (превью, px)
                                                                     └──► pptx-export (PptxGenJS, дюймы)
```

Сцена — список прямоугольников, текстов и изображений с координатами в дюймах и уже подобранным размером шрифта. Превью и PPTX строятся по **одной сцене**, но браузер и PowerPoint могут по-разному переносить текст и подставлять шрифты. В PPTX текст и фигуры — настоящие редактируемые объекты, не скриншот слайда; логотип темы при наличии остаётся изображением.

## Корпоративная тема

Всё оформление слайдов — в одном файле **`frontend/src/theme/presentation-theme.ts`**. Сейчас там **временная нейтральная тема**: цвета и шрифты не являются официальными, логотипа нет. Интерфейс показывает бейдж «Временная тема», пока `isOfficial: false`.

Когда появится брендбук:

1. Замените `colors` (HEX), `fonts.heading` / `fonts.body` (имя шрифта, как оно называется в PowerPoint), при необходимости размеры в `typography` и поля в `spacing`.
2. Логотип: положите файл в `frontend/public/`, например `frontend/public/logo.png`, и укажите
   ```ts
   logo: { src: '/logo.png', width: 1.4, height: 0.6, onDarkSlides: true, srcOnDark: '/logo-white.png' }
   ```
   Размеры — в дюймах; изображение вписывается с сохранением пропорций.
3. Текст в колонтитуле — `footer.text`, номер слайда — `footer.showSlideNumber`.
4. Поставьте `isOfficial: true` и `name`.
5. Если сменился шрифт — перепроверьте коэффициенты ширины символа в `frontend/src/layouts/text-fit.ts` (там описано, как их замерить), иначе подбор размера будет неточным.
6. Схематичные миниатюры макетов в `frontend/src/features/editor/LayoutPicker.tsx` нарисованы цветами временной темы — обновите их под новую гамму.

Расположение элементов на слайдах (типовые макеты) задаётся в `frontend/src/layouts/definitions/*.ts`.

> **Шрифты.** PPTX хранит только имя шрифта. Если у сотрудника он не установлен, PowerPoint подставит замену. Для корпоративного шрифта его нужно установить на рабочие места.

## Как добавить новый макет

Пример: макет «Цитата».

1. **Схема** — `frontend/src/domain/presentation.ts`:
   ```ts
   export const quoteSlideSchema = z.object({ ...slideBase, layout: z.literal('quote'), quote: text(600), author: optionalText(200) })
   ```
   Добавьте её в `slideSchema` и в `generatedSlideSchema` (с `.extend(optionalId)`).
2. **Определение** — `frontend/src/layouts/definitions/quote.ts` по образцу `section.ts`: `label`, `description`, `icon`, `fields` (поля правой панели), `fromContent`/`toContent` (перенос текста при смене макета), `buildScene` (геометрия в дюймах; используйте `fittedText` из `chrome.ts`).
3. **Реестр** — строка в `frontend/src/layouts/registry.ts`.
4. Готово: макет появится в выборе макета и меню «Добавить», в превью и в PPTX. Тест `у каждого макета из схемы есть определение в реестре` подскажет, если что-то забыто. По желанию — схематичная миниатюра в `LayoutPicker.tsx` (иначе показывается иконка).
5. Согласуйте макет с backend и ML: обновите `backend/app/presentations/schemas.py`, [ML-контракт](ML_CONTRACT.md), JSON Schema (`npm run schema` из `frontend/`), общую фикстуру и контрактные тесты обеих сторон. Одной регистрации во frontend для HTTP-режима недостаточно.

Backend, из `backend/`:

```bash

uv run --locked pytest -q
```

Без явных `PM_TEST_DATABASE_URL` и `PM_TEST_REDIS_URL` интеграционные тесты пропускаются. Для их запуска нужна **отдельная пустая БД с именем, оканчивающимся `_test`**, и отдельный тестовый Redis: тесты применяют миграции, очищают таблицы и запускают настоящие Celery-процессы. Из `backend/`:

## Production-эксплуатация

- Настройки: `PM_ENVIRONMENT=production`, `PM_ML_ADAPTER=module`, реальные URL PostgreSQL/Redis из секретного окружения, `PM_ALLOWED_ORIGINS=["https://YOUR_HOST"]`. Реальный ML-пакет должен быть установлен в backend-образ. Предпочтителен один origin; cookie/CORS при раздельных доменах проверяются в целевом браузере.
- HTTPS обязателен. Для отдельного API-домена задаётся `PM_ALLOWED_HOSTS=["api.YOUR_HOST"]`; health-check должен передавать разрешённый Host. Origins — точные HTTP(S)-origin без путей/wildcard, hosts — без схемы/порта/wildcard.
- За reverse proxy включайте Uvicorn `--proxy-headers --forwarded-allow-ips=<IP доверенного proxy>`, иначе IP-лимиты будут общими. Proxy должен перезаписывать `X-Forwarded-For` адресом клиента. В локальном Compose доверие `*` допустимо только потому, что API не публикуется на хост и все контейнеры внутренней сети доверенные; при прямом доступе к API так делать нельзя. Backend-образ по умолчанию не доверяет proxy-заголовкам.
- Регистрация в production закрыта по умолчанию. `PM_REGISTRATION_ENABLED=true` открывает её явно; нужен контролируемый допуск. При открытой регистрации ответ 409 о занятом логине позволяет проверить существование имени.
- Нужны непривилегированная роль PostgreSQL и ACL Redis. Backend запрещает production-роль БД `postgres`/`root`, пустые/демонстрационные пароли и Redis без пароля. Для удалённых подключений обязательны PostgreSQL `sslmode=verify-full` и Redis `rediss://` с доверенным CA. Подмена адреса/credentials через query URL запрещена; проверка URL не заменяет настройки серверов.
- Миграции выполняются до запуска API/worker. Redis — с персистентностью и `noeviction`; Celery result backend не нужен, visibility timeout должен превышать deadline задания.
- Отдельно контролируются API, оба worker и единственный Beat: положительный ready не доказывает работу очередей/GPU. Начальная concurrency ML-worker — 1; память/GPU/egress, файловый доступ и доступные ML секреты ограничиваются инфраструктурой.
- Пулы SQLAlchemy на процесс: API 5 + overflow, worker 2 + overflow. Ожидание пула/подключения — 2 с, TCP user timeout — 5 с, SQL statement — 5 с, lock — 2 с; суммарный бюджет соединений учитывает все процессы. Эти пределы не ограничивают длительность вычисления ML или отдельный запуск Alembic.
- Остановка/обновление — SIGTERM и warm shutdown с ожиданием активных задач в пределах deadline, затем запуск новых worker/Beat. Не очищать брокер/таблицы: queued восстановит maintenance, потерянные running завершаются ошибкой без автоматического ML-повтора.
- Логи — request_id/job_id, типы ошибок и длительности без приватных payload, URL и traceback. Не включать DEBUG Celery. Мониторить queued/running/deadline/heartbeat, оба worker/Beat, длительность фаз, ошибки, БД/Redis/диски.
- Обязательны backup PostgreSQL и проверка восстановления. Сроки хранения текущих документов и администраторское удаление согласуются отдельно: автоматического удаления нет. Аудит зависимостей/образов проводится регулярно.

## Ограничения

- **Мастер-слайды.** PptxGenJS создаёт слайды кодом и **не может использовать мастер-слайды и макеты из готового .pptx/.potx-шаблона**. Оформление воспроизводится по значениям из темы: цвета, шрифты и расположение совпадут, но в PowerPoint у слайдов не будет «корпоративного» мастера и макетов из меню «Макет». Если заказчик потребует строгого соответствия мастер-шаблону, сборку PPTX нужно перенести на бэкенд (например, `python-pptx` поверх официального шаблона). Контракт данных при этом остаётся тем же — фронтенд отправит презентацию на сервер вместо локальной сборки.
- **Подбор шрифта приблизительный.** Размер оценивается по средней ширине символа для Arial, а не измеряется PowerPoint. Если текста слишком много, шрифт уменьшается до аварийного минимума (9 pt), но переполнение всё равно возможно. Экспорт предупреждает, но не блокирует скачивание; ручное разделение доступно только в mock, в HTTP нужна команда сократить контент. В PPTX у текстовых полей включено «Сжимать текст при переполнении» для дальнейших правок в PowerPoint.
- **Демо-генератор — не ИИ.** Он не пересказывает и не сокращает текст по смыслу, а раскладывает исходные формулировки.
- **Mock-хранение — только в браузере** (`localStorage`): один черновик. В HTTP документы хранятся в PostgreSQL, но списка презентаций, истории версий и API архива нет; браузер запоминает ссылки на текущую работу, а не её содержимое.
- **Изображения, диаграммы и таблицы** на слайдах не поддерживаются.
- **DOCX** читается в браузере (mammoth): сохраняются заголовки, абзацы и списки; таблицы и картинки игнорируются. Старый `.doc` не поддерживается.
- **ML ещё не подключён.** Серверная fixture проверяет интеграцию, но не смысл команд, качество доклада или близость к запрошенному числу слайдов.
